= How to build the Nine Nines website

The published HTML is the source. Hugo is gone.
`docs/en` is generated by this Makefile and then committed.
`_build/tmp` is gitignored.

== Preview

[source,sh]
----
make -C _build serve
----

Open http://localhost:8080/. The server is `_build/server`.
A directory URL without a trailing slash redirects to one.
Relative manual links need that slash.

== Documentation

Versions are listed in two places in `_build/Makefile`.
Keep them the same.

The `docs-html-project` lines at the bottom take the doc versions,
then the git refs in the same order, then `true` when the project
has a guide. Cowlib has no guide, so its last argument is empty.

`published` inside `docs-man-links` is the same versions, newest
first. The first word is the fallback when a dependency version
is not published.

Keep three versions of each project. Adding one means dropping
the oldest of that line, except Ranch. Keep Ranch 1.8 and the two
newest 2.x versions. Cowboy's Makefile pins `dep_ranch` to 1.8.x,
and the Cowboy docs link to that published manual. Dropping 1.8
would send those links to the newest Ranch.

Cowlib's Makefile has no `dep_cowboy` or `dep_gun` line. The
`cowlib:cowboy:` and `cowlib:gun:` cases map each published Cowlib
version to the Cowboy and Gun released with it. Add the new Cowlib
version and delete the case for the version you drop. Without a
case, Cowlib links to the newest Cowboy and Gun.

Other cross-project links read `dep_<name> = git <url> <ref>` from
that tag's Makefile. `dep_cowboy_commit` does not match. A ref such
as `2.22.0` becomes version `2.22`. If that version is in
`published`, the link uses it. Otherwise the Cowlib cases apply,
then the first published version.

The recipes clone into `_build/tmp/manual/<project>` and
`_build/tmp/guide/<project>` only when the clone is missing. They
then run `git checkout -f` and `git reset --hard`. They do not
fetch. Fetch the tags first, or a new tag will not check out:

[source,sh]
----
for d in _build/tmp/manual/* _build/tmp/guide/*; do
    git -C "$d" fetch origin --tags
done
make -C _build -j8 docs
----

The first build also clones Asciideck into `_build/tmp/asciideck`.

`make docs` rewrites every version still in the list, because each
page's version switcher is that full list. It does not delete a
version you removed. Delete that tree yourself:

[source,sh]
----
rm -rf docs/en/<project>/<version>
----

Search the articles for `/docs/en/<project>/<version>/` and remove
those anchors. Leave the surrounding words.

`source-highlight` has no `make` language. A `[source,make]` block
is published as the text `could not find a language definition for
make`. The language name is `makefile`. Gun's Getting Started page
still has `[source,make]` in `doc/src/guide/start.asciidoc`; the
2.6, 2.7, and 2.8 HTML was patched in place. The Erlang.mk and Relx
article was patched the same way. Regenerating either page from
`[source,make]` puts the error back.

Guide chapters, not `book.asciidoc`, rewrite `link:man:`:

* `link:man:cowboy(7)` and the other `*(7)` pages go through
  `man_links` to the other project's manual.
* `link:man:module:function` becomes `module.function`, then a
  same-project manual URL
  `/docs/en/<project>/<version>/manual/<page>`.
* `otp_links` rewrites bare `ssl(7)`, `ssl(3)`, `gen_tcp(3)`, and
  `inet(3)`. It does not rewrite `link:man:ssl(3)`.
* `xref:` becomes `link:../` and `image::` becomes `image::../`.
* `.asciidoc` and `.sty` files are not copied into the guide.
  Other files next to the chapters are.

Manual pages get the same man and OTP rewrites. Same-project
manual links stay relative.

`_build/templates/head.html` and `foot.html` wrap every generated
page. The version list and the guide or manual links are injected
at `{{VERSION_LINKS}}` and `{{DOC_LINKS}}`.

After the build, update by hand:

* `index.html`, the latest guide and manual buttons
* `docs/index.html`, prepend the new version and drop the removed one
* `docs/index.xml`, and the doc items in `index.xml`.
  Use the UTC dates described under Articles.

== Articles

One short page covers the whole release. Name it after the Cowboy
version, as in `articles/cowboy-2.21.0/index.html`. Copy the
previous combined article.

The title looks like `Cowboy 2.21, Cowlib 2.22, Gun 2.8, Ranch 2.4`.
The date line is
`<span class="year">2026</span> <span class="day-month">09 Nov</span>`.

Read the migration guides from the tags before writing. Say that
Cowboy and Gun update Cowlib and must be upgraded with it. Do not
say they require the new Ranch. Cowlib has no migration guide.
Link the guides for the projects that have one:

* `/docs/en/cowboy/2.21/guide/migrating_from_2.20/`
* `/docs/en/gun/2.8/guide/migrating_from_2.7/`
* `/docs/en/ranch/2.4/guide/migrating_from_2.3/`

Keep the closing sponsors and Discord sentences used by the recent
articles.

Also update:

* `articles/index.html` and `articles/page/2` through `page/4`.
  Twenty posts per page. Prepend the new post on page 1 and move
  the last post of each page onto the next page.
* `#articles-nav` on every article page. Ten items. Prepend the
  new article and drop the oldest.
* `articles/index.xml`, `docs/index.xml`, and `index.xml`.
  New `pubDate` and `lastBuildDate` values are UTC only.
  The hour is a placeholder: the release day at `07:00:01 +0000`,
  for example `Tue, 10 Nov 2026 07:00:01 +0000`. Leave the
  existing `+0100` and `+0200` stamps unchanged. The description
  is plain text, one paragraph per line, with no HTML.

Leave Ranch's Makefile entries unchanged when Ranch is not part
of the release.

== Check

With the preview server running, open the new article, the home
buttons, `docs/index.html`, one new manual, and one new migration
guide. The dropped version should 404. A kept page's version list
should contain the new version and not the dropped one. Cowlib's
manual should link to the Cowboy and Gun versions from its cases.
Cowboy should link to the new Cowlib and to Ranch 1.8.
